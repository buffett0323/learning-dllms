Fast-dLLM, dKV-Cache and Sparse-dLLM speed up one request. dLLM-Serve asks what breaks when a GPU serves many at once, and fixes three things:

- **Logit Decomposition** (§4.3): compute the [B, L, V] logits in chunks, so the activation peak is small and the freed memory goes to the KV pool.
- **Phase-Multiplexed Scheduler** (§4.4): schedule per Refresh/Reuse phase, not per request.
- **Head-Centric Sparse KV Cache** (§4.5): each head keeps its own top-k tokens, stored contiguously.

Result: 1.61–1.81× throughput on RTX 4090 and 1.60–1.74× on L40S over the best baseline, with tail latency down almost 4× under heavy load.

<Annotation page={1} line={41} text="monolithic logit computation tensor dominates GPU memory,">
**The Memory Footprint Crisis.** The last layer turns each position into logits over the whole vocabulary. AR needs them only for the newest token, a $[B, 1, V]$ tensor. A dLLM predicts every position each step, so it materializes $[B, L, V]$. For LLaDA-8B with $B = 16$, $L = 2048$, $V = 126{,}464$ in FP16 that is $16 \cdot 2048 \cdot 126{,}464 \cdot 2$ bytes $\approx 8.3$ GB (p. 4), a third of a 4090.

The tensor lives for one projection only, but the engine must reserve memory for the peak, and every GB reserved is taken from the KV pool, so fewer requests fit. The fix: compute logits in serial chunks of at most `max_num_logits` tokens, which caps the peak.
</Annotation>

<Annotation page={1} line={44} text="distinct resource oscillation" color="blue">
**Refresh vs Reuse.** The two kinds of pass in Fast-dLLM's Algorithm 1 ([animated here](../fast-dllm/)):

- **Refresh** (lines 2, 19): all $L$ tokens run and $Q, K, V$ are recomputed for the full sequence (Eq. 3). Big matrix multiplies: compute-bound, like AR prefill.
- **Reuse** (line 6): only the $B$ tokens of the block run; their queries read the cached $K, V$ of everything else (Eq. 4). Little math per byte loaded: bandwidth-bound, like AR decode.

Each request alternates: one Refresh, then several Reuse steps per block. A scheduler that reserves the Refresh peak for a request's whole life leaves it idle during Reuse. dLLM-Serve fills a token budget each iteration and admits new Refresh work into the room freed by requests in Reuse.
</Annotation>

<Annotation page={2} line={77} text="guided eviction (Sparse-dLLM [18]) or head-specific sparse">
Both drop low-importance context, mostly masks, which carry little information (§2.4).

- **Sparse-dLLM:** sums each token's attention score over heads, keeps one shared top-$k$ set for all heads and evicts the rest from the cache. Regular memory layout, but a token that matters to one head only can be dropped.
- **SparseD:** a different set per head, which keeps accuracy, but done with attention masks: the full KV is still stored and loaded (§3.3).

dLLM-Serve keeps per-head selection and physically stores only the kept tokens, packed densely (§4.5).
</Annotation>

<Annotation page={3} line={47} text="attention distribution is inherently sparse">
**Sparse attention.** Each query's softmax weights over the keys sum to 1, but most of the weight lands on a few keys and the rest get almost none. Masks are the extreme case: every [MASK] has the same embedding, so they say little. Dropping the K/V of near-zero keys barely changes the output and saves memory and bandwidth.
</Annotation>

<Annotation page={3} line={56} text="Current methods such as Sparse-dLLM [18] enforce a single">
**Sparse-dLLM** evicts context tokens from the KV cache. For every head $h$ and context token $j$ it scores how strongly the block's queries match $j$'s key (max-pooled over a small window, so neighbors of an important token survive too), then **sums over heads** (Eq. 5). That gives one importance score $S_j$ per token, and the top $k$ tokens are kept for **all** heads: one global sparsity pattern.
</Annotation>

<Annotation page={3} line={8} text="selects one shared top-k index set I from S">
$\mathcal{I}$ is the list of positions kept: the $k$ indices $j$ with the largest $S_j$, with $k = rL$. Every head gathers $K[:, \mathcal{I}]$ and $V[:, \mathcal{I}]$, so all heads keep the same tokens, in the same slots. dLLM-Serve instead picks $\mathcal{I}_h$ per head (Eq. 6).
</Annotation>

<Annotation page={4} line={58} text="it implicitly optimizes for average relevance" color="pink">
**Why the sum hurts.** Summing over heads ranks tokens by how much heads need them on average. A token that one head relies on (say, a matching bracket) but the other 31 ignore gets a low sum and is evicted, and that head loses its main input. In the demo at the top, head 4 keeps only a fraction of its attention under the shared set.

The gain from sharing is layout: one index set, so every head's kept K/V sit at the same positions and one regular gather serves all heads. Measured cost (§6.4, Fig. 6): at $r = 10\%$, HumanEval drops to 7.9% pass@1 with the shared set vs 20.1% per head; GSM8K 40.0% vs 75.1%.
</Annotation>

<Annotation page={5} line={35} text="activation footprint of the output projection">
**Footprint** = how much GPU memory something takes. GPU memory holds three things: the weights, the KV cache, and **activations**, the temporary tensors a forward pass creates and then frees. The **output projection** (LM head) is the last matrix multiply, hidden size $d$ → vocabulary $V$, which produces the logits. Its output, $N \times V$ for $N$ tokens, is by far the largest activation: $N = 16 \times 2048$ tokens gives 8.3 GB. The engine reserves memory for the largest activation at startup, so this one tensor sets the reservation.
</Annotation>

<Annotation page={6} line={5} text="Logit Decomposition. To break this dependency" color="green">
**Logit Decomposition.** Decoding only needs, per token, the chosen token id and its confidence, not the full row of $V$ logits. So instead of one $[N, d] \times [d, V]$ multiply:

1. take the next `max_num_logits` hidden states,
2. compute their logits,
3. argmax / sample, keep the ids and confidences,
4. drop the logits tensor, and repeat.

"Releasing the buffer" is just letting that tensor go out of scope; PyTorch's allocator then hands the same memory to the next chunk. Peak memory is chunk × $V$ instead of $N \times V$ (16× smaller for a 2048-token chunk of the 32,768 above). Same FLOPs, a few more kernel launches. Step through it in [P04](../../posts/batching/#the-logit-spike).
</Annotation>

<Annotation page={6} line={7} text="4.5 Head-Centric Sparse KV Cache Management">
**Head-centric** = sparsity is chosen per attention head. Each head $h$ ranks context tokens by its own score $S_{h,j}$ (Eq. 6) and keeps its own top-$k$ set $\mathcal{I}_h$. All heads keep the same **number** of tokens, $k = rL$, but not the same tokens.
</Annotation>

<Annotation page={6} line={26} text="Decoupling Logical Sparsity from Physical Layout">
**How the decoupling works.** *Logical* = which tokens a head keeps; *physical* = where their K/V sit in memory. At each Refresh, for every head, gather the K/V at $\mathcal{I}_h$ and copy them into slots $0 \dots k-1$ of a dense $[N_\text{heads}, rL, D_\text{head}]$ buffer, then throw the indices away. Rows hold different tokens but have the same length, so the buffer is a plain rectangle.

This works because attention does not need the original positions: RoPE is applied to the keys before storing, so position is already inside each key, and softmax over a set of keys does not depend on their order. Reuse steps then run ordinary dense attention (FlashAttention) over each head's $k$ slots, with no index lookups. Compare SparseD: same per-head choice, but via masks over the full $[N_\text{heads}, L, D_\text{head}]$ cache, so no memory is saved.
</Annotation>

<Annotation page={6} line={41} text="the system pre-allocates a fixed block of rL">
**Retention ratio $r$:** the fraction of a request's $L$ context tokens whose K/V each head keeps, so $k = rL$ and the cache is $r$ times the dense size. The experiments use $r = 0.5$ (Sparse-dLLM's default). Lower $r$ fits more requests in memory but loses accuracy, and per-head selection loses much less: on GSM8K its $r = 10\%$ matches the shared set at $r = 20\%$ (§6.4).
</Annotation>
